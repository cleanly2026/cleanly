<objective>
Close the two cross-cutting gaps left over from Plan 02 (Fly deploy) and Plan 03 (Vercel deploy):

1. **R2 CORS (VCL-06)** — Apply an explicit CORS policy to both R2 buckets. `AllowedHeaders` MUST list `content-type` explicitly, NOT `"*"`. Wildcard breaks Safari preflight for presigned PUT uploads.

2. **API CORS allowlist (VCL-05)** — Plan 02 deployed the API with placeholder origin values. Now that Plan 03 has produced the real Vercel URLs, write them into Fly secrets so `@fastify/cors` AND the separately-configured Socket.io CORS both accept the deployed frontends.

This plan depends on BOTH Plan 02 (Fly apps must exist) and Plan 03 (Vercel URLs must exist), so it sits in Wave 3.

Purpose: Without this plan, a user on cleanly-customer-staging.vercel.app cannot talk to cleanly-api-staging.fly.dev — CORS rejects them. Without explicit `content-type` in R2 CORS, Safari users cannot upload photos. Both are latent failures that don't surface until a real user tries the app.

Output: R2 CORS applied to both buckets, Fly secrets set on both apps, a runbook documenting the commands, verified with a real cross-origin fetch.
</objective>

```json
[
  {
    "AllowedOrigins": [
      "https://cleanly-customer-staging.vercel.app",
      "https://cleanly-customer.vercel.app",
```

**CRITICAL:** `AllowedHeaders` MUST be `["content-type"]` — NEVER `["*"]`. The single-string-only rule is the entire reason VCL-06 exists as a standalone requirement. If the executor has a reflex to "be more permissive" and substitutes `"*"`, Safari presigned PUT uploads will fail preflight.

If Plan 03 produced different URLs (e.g., `cleanly-customer-app-staging.vercel.app` instead of `cleanly-customer-staging.vercel.app`), substitute the REAL URLs into `AllowedOrigins` before applying.

Do NOT include `https://cleanly-api*.fly.dev` URLs — CORS is about the ORIGIN making the request, which is the browser's origin (Vercel), not the API that signs the URL.
